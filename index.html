Study session tracker: research notes

By Shawn Murray, IS218 Fall 2026, NJIT. These notes record what I read, what I concluded, and what I still have to prove before I build.

Question and audience

Which web stack lets me deliver a complete account journey (sign up, log a study session, see a private dashboard, change my account) with the least security risk, and how will I test it?

Audience: my instructor and classmates reviewing the Plan, and me when I start building. They should come away knowing why I picked this stack, what I verified, and what I'm still assuming.

The app: a signed-in user logs study sessions (subject, minutes, optional focus rating), and a private dashboard shows weekly totals, time per subject and recent sessions. A new user sees a friendly empty state.

Findings, kept separate

Facts (each needs a source I have read)

FactDjango includes an authentication system covering users, sessions and password handling. Source: Django docs: using the auth system.
FactDjango stores passwords as salted hashes, not plain text. Source: Django docs: using the auth system. OWASP's Password Storage Cheat Sheet describes why salted hashing is the safe approach.
FactDjango ships a view for changing passwords (PasswordChangeView) and a helper that keeps the user signed in after the change (update_session_auth_hash). Source: Django docs: using the auth system.

Interpretations (my reading of the facts)

InterpretationBecause Django supplies sign-in, hashing and password change, I write less security-critical code myself, which lowers risk for a first account system.
InterpretationKeeping the stats math in plain functions, separate from views, makes independent tests easier to write.

Audience and presentation approaches

  1. Plain dashboard: tables and totals, quick to build and easy to test.
  2. Visual dashboard: charts of weekly minutes and subjects, more engaging but more to test.

Chosen: plain dashboard, because it is quicker to build and easier to test, which keeps the first slice achievable by Review 2.

Decision and what it feeds

Stack: Python, Django, SQLite, Django templates, Playwright for browser tests, GitHub Actions for CI.

Five stories

  1. As a visitor, I can sign up and see clear errors when my input is invalid.
  2. As a user, I can sign in and out.
  3. As a user, I can log a study session with validated subject and minutes.
  4. As a user, I can see only my own totals and recent sessions, with an empty state when I have none.
  5. As a user, I can change my display name and my password using my current password.

Design decision to test

Compare computing stats with a simple function against a Strategy pattern for different summaries (weekly, by subject). I will keep whichever is easier to read and test, and record why.

Planned experiment

AI weekly summary (a short generated recap of the week's sessions). Stopping point: end of week 3. Fallback: the manual log form, which stays fully working.

Rough data sketch

  • User: email, display name, password hash
  • StudySession: user, subject, minutes (1 to 600), focus rating (optional), notes, created time
  • Every query filters by the signed-in user.
